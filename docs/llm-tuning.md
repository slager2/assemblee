# Настройка локального llama-server

Железо: ноутбук, RTX 3050 Laptop 6 GB (Vulkan-устройство `Vulkan1`), Ryzen 5 8645HS (6/12),
14 GB RAM. Сборка llama.cpp b11426 (Vulkan, с turbo-кэшами). Модель агента:
`Qwen3.5-4B-Q4_K_M.gguf` + `Qwen3.5-4B-mmproj-F16.gguf` (зрение).

Запуск: `scripts/serve_llm.sh start agent` (или `planner`), `stop`, `status`.
PID и логи лежат в `.cache/` (`llm-server.pid`, `llm-agent.log`, `llm-planner.log`).
Бенчмарк: `python3 scripts/bench_llm.py --port 8011 --label X [--rounds 15] [--concurrent] [--user-turn]`.

## Что меряет bench_llm.py

Промпт как у агента: system + 18 инструментов (JSON-схемы) + история из `probe_clip`
вызовов с транскриптами. `--rounds 10` = 19.8k токенов, `--rounds 15` = 28.4k.

| Метрика | Что это |
|---|---|
| pp t/s | обработка холодного промпта (уникальный префикс, кэша нет) |
| TTFT ход | следующий ход агента: история + tool call + tool result (~115 новых токенов) |
| TTFT после ответа | ход после того, что модель реально сгенерировала (проверка, что её токены переиспользуются) |
| tg t/s | генерация ответа `set_timeline` (~350-400 токенов tool-call) на глубине 20k/28k |
| зрение | PNG 540x960 + вопрос, ответ по JSON-схеме (~30 токенов) |
| ход после зрения | ход агента сразу после запроса со зрением |

Все замеры ниже сделаны **от сети** (AC). На батарее GPU работает заметно медленнее
(pp ~700-850, tg ~21-26 t/s) и результаты сильно гуляют. Разброс между прогонами от сети
около ±3%.

## Выбранная конфигурация (`agent`)

```
llama-server -m Qwen3.5-4B-Q4_K_M.gguf --mmproj Qwen3.5-4B-mmproj-F16.gguf \
  --device Vulkan1 -ngl 99 -c 65536 -ctk q8_0 -ctv q8_0 -fa on \
  --parallel 2 --kv-unified --no-cache-idle-slots --cache-ram 1024 \
  -b 2048 -ub 512 -t 6 --poll 0 --jinja --reasoning off --no-webui
```

Почему:

- **Сырые скорости упираются в железо**: pp ~1000 t/s и tg ~30 t/s на 20k одинаковы почти для
  всех конфигов (f16/q8, 32k/49k/64k, ub 512-2048). Выигрыш не в t/s, а в том, чтобы никогда
  не пересчитывать историю.
- **Главная проблема baseline**: один слот. Запрос со зрением занимает его, KV агента уходит
  в RAM-кэш (`--cache-ram`). В f16 состояние 20k истории весит ~820-890 MB, 28k — больше
  лимита 1024 MB, и оно просто выбрасывается: следующий ход агента пересчитывает всю
  историю, **20-30 s** вместо 0.13 s. Каждый `look_at_frame` стоил полминуты.
- **`--parallel 2 --kv-unified`**: зрение идёт во втором слоте общего пула KV, слот агента
  не трогается. Зрение можно запускать параллельно с ходом агента: ответ зрения 0.95 s,
  поток агента за это время теряет ~1 s (29.3 против 30.0 t/s на весь ответ; на 28k-глубине
  в f16 −10%).
- **`--no-cache-idle-slots`**: иначе сервер при каждом новом запросе выгружает простаивающий
  слот агента в RAM и потом грузит обратно (0.28 s, а на батарее один раз 10 s). С 2 слотами
  это не нужно.
- **q8_0 KV**: по скорости не отличается от f16 (в пределах шума на 20k и 28k), но вдвое меньше
  памяти. Это даёт 64k контекста целиком на GPU вместе с mmproj (4.88 GB из 6.1, ~1.2 GB
  запаса на compute-буфер зрения), и RAM-кэш промптов ~590 MB на 20k вместо ~850 MB.
  `--cache-ram 1024` оставлен как потолок (прошлый раз кэш без лимита дорос до 7 GB).
- **`-ub 512`**: 1024/2048 не быстрее (1014 против 985 t/s, шум), но съедают +130-420 MB VRAM.
- **`-t 6 --poll 0`**: всё на GPU, потоки CPU на скорость не влияют; без активного поллинга
  CPU меньше греется и не отбирает тепловой бюджет у GPU ноутбука.

Итог против baseline: те же ~1000 t/s pp и 30 t/s tg, но контекст **64k вместо 32k**,
VRAM **4.88 вместо 4.73 GB** при вдвое большем контексте, ход агента после зрения
**0.13-0.15 s вместо 20-30 s** (в 150-200 раз), зрение **1.6 s отдельно / 0.95 s параллельно**
вместо 2.3 s и без блокировки агента.

## Важно для харнесса агента

- **Не добавлять новые `user`-сообщения в середине сессии.** Шаблон Qwen3.5 рендерит
  assistant-ходы после последнего user-сообщения с пустым `<think>\n\n</think>`, а до него без.
  Новое user-сообщение меняет рендер всей истории сразу после первой задачи, и модель
  (гибридная, с рекуррентными слоями) не может переиспользовать префикс: пересчёт 17.6k из
  19.8k токенов, **18.3 s** вместо 0.53 s. Подсказки и «следующий шаг» класть в `content`
  tool result.
- Историю не переписывать (не сокращать старые tool results задним числом): любое изменение
  в середине = пересчёт всего после него, частичного отката у рекуррентного состояния нет
  (только чекпоинты, см. `--ctx-checkpoints`).
- Формат tool call у Qwen3.5 через `--jinja` — XML-подобный (`<function=...><parameter=...>`),
  сервер сам отдаёт OpenAI `tool_calls`. Если ответ обрезан `max_tokens`, сервер вернёт 500
  на следующий запрос с этим вызовом (невалидный JSON аргументов): ставить запас по `max_tokens`.
- Запрос зрения: отдельный запрос без tools, `response_format: json_schema`. С двумя
  слотами его можно слать параллельно ходу агента.

## Что не сработало

- **Спекулятивное декодирование с Qwen3.5-0.8B** (токенизатор совместим, accept 79-86% на
  tool-call JSON): генерация **падает вдвое** (13.9-15.4 против ~25 t/s в том же состоянии
  питания), pp тоже падает (драфт пересчитывает весь промпт), +0.9 GB VRAM. Qwen3.5 гибридная
  (Gated DeltaNet + attention): проверка черновика требует отката рекуррентного состояния,
  на 3050 это дороже, чем выигрыш.
- **`ngram-simple`**: accept 7%, медленнее.
- **MTP** (`--spec-type draft-mtp`): в этих GGUF нет MTP/NextN-тензоров.
- **turbo3 KV**: экономит ещё ~350 MB, но pp −14%, tg −11%. Смысл только если не хватит VRAM.
- **f16 KV на 64k**: сервер падает при первом же запросе со зрением (не хватает VRAM на
  compute-буфер mmproj). f16 49k работает (5.3 GB), но запаса почти нет, и q8 64k не медленнее.
- **`-ub 1024/2048`**: без выигрыша, только VRAM. `-ub 256` медленнее.
- **`-cms 0`** (чекпоинты чаще): на проблему с user-сообщением не влияет, причина в шаблоне.
- `--fit` в логе пишет «failed to fit params ... restoring the pre-fit parameters»: это
  нормально при явном `-ngl 99`, все слои на GPU.

## Planner (9B)

`serve_llm.sh start planner`: 9B IQ4_XS, 32k, q8_0, 5.17 GB VRAM, ~18 t/s генерации
(0.6x от 4B), pp ~610 t/s. Подходит для редкого шага планирования; свап с агентом ~4-5 s,
но после свапа кэш промпта агента пропадает: первый ход после возврата пересчитает всю
историю (~20-30 s на 20-28k). Поэтому переключаться стоит в начале сессии (план), а не
на каждом ходе.

Сейчас профиль `planner` — `--parallel 2 --kv-unified --no-cache-idle-slots` (общий пул 32k):
агент строит две секции параллельно на 9B при той же VRAM. `--planner 9b` в агенте свапает
ровно два раза: 4B (каталог) → 9B (план, сборка, полировка) → 4B (режиссёр, проверка, экспорт);
каждая фаза начинает с нового промпта, так что пропажа кэша после свапа ничего не стоит.

## Размышление (thinking) Qwen3.5 по запросу

Сборка b11426: размышление включается **в каждом запросе** полем
`chat_template_kwargs: {"enable_thinking": true}`; бюджет — `reasoning_budget_tokens: N` (по
исчерпании сервер сам закрывает `</think>`, перед этим вставляет `reasoning_budget_message`).
`--reasoning off` задаёт только значение по умолчанию: поле запроса его перекрывает, поэтому
обычные профили `agent`/`planner` тоже умеют думать по запросу. Профили `agent-think` /
`planner-think` (`--reasoning auto --reasoning-format deepseek --chat-template-kwargs
'{"enable_thinking":false}'`) делают то же явно: по умолчанию не думают (проверено запросом без
kwargs), думают по запросу. `LLM.chat/json(think=True, think_budget=N)` всегда шлёт
`reasoning_format: deepseek`: мысли приходят в `message.reasoning_content`, `content` — чистый
JSON. Грамматика `json_schema` в этой сборке строится как `reasoning << content(schema)`, то есть
действует на ответ после мыслей; проверено живьём (enum соблюдены, `<think>` в content нет).

| Модель | think | бюджет | токены мыслей | время запроса (раскадровка, ~150 ток. ответа) |
|---|---|---|---|---|
| 4B | нет | — | 0 | 7.3 s |
| 4B | да | 256 | 263 | 13.5 s |
| 4B | да | 1024 | 1031 | 33.6 s |
| 9B | нет | — | 0 | 6.8 s |
| 9B | да | 256 | 263 | 21.6 s |
| 9B | да | 1024 | 1031 | 60.5 s |

Модель почти всегда выбирает весь бюджет (мысли по-английски, «Thinking Process: …»).

Свап профилей (`serve_llm.sh start X`, модели в page cache): planner-think 4.6 s, agent-think 4.3 s,
planner 3.5 s, agent 3.5 s. VRAM: 9B (2 слота, общий пул 32k) 5.19 GB, 4B + mmproj 4.83 GB.
